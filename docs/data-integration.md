# Замена демонстрационных данных

UI работает с доменной моделью и TripView. Происхождение хранится у каждого значения. Метка демо не снимается сменой переменной.

1. Получить у команды схему и способ доступа: JSON/CSV, SQL либо HTTP. Уточнить лицензии медиа, источник отзывов, валюту, единицы, актуальность и stable IDs.
2. Сопоставить hotel-room-place-media-evidence. Не использовать название отеля как внешний ID. Сохранить таблицу externalId -> internalId.
3. Написать адаптер CatalogRepository. На входе валидировать DTO через Zod, например externalHotelSchema в src/data/adapters/catalog.ts отвергает USD и метры вместо минут. Добавить полную схему реального источника, тесты корректных и ошибочных данных.
4. Реализовать GeoProvider отдельно, если маршруты не поставляет каталог. При реальном вычислении сохранить метод, входные evidence, геометрию, метры, минуты и ограничения. По прямой и по маршруту разные значения.
5. Подключить AgentProvider и RecommendationProvider через src/data/providers.ts. Контракт будущего агента ниже и в api-contract.md. Ключи только на сервере. Текст отзывов и реплик внешних источников никогда не выполняется как команда.
6. Перенести TripRepository на БД при масштабировании. Преобразование каталога не удаляет поездки/голоса. Объект с исчезнувшим ID требует явной обработки и повторного подтверждения, а не незаметной замены отеля.
7. Запустить доменные, контрактные и сквозные проверки. Пройти те же deep links, сравнение, unknown/conflicting/stale и независимые сессии.

## DeepSeek уже подключён

`DeepSeekAgentProvider` реализует текущий `AgentProvider`, JSON валидируется до применения пожеланий. Настройки: `AGENT_PROVIDER=deepseek`, `DEEPSEEK_API_KEY`, `DEEPSEEK_MODEL=deepseek-flash`. Секреты только в `.env` на сервере. Внешнему API передаётся свой диалог и нормализованные общие пожелания, без чужих личных сообщений. Рекомендации, каталог и гео всё ещё fixture. Дополнительные сведения и реальный smoke-тест находятся в README и `docs/verification-deepseek.json`.

## Интерфейсы

Полные TypeScript-сигнатуры находятся в src/data/contracts/index.ts. Будущий ApiCatalogRepository реализует listHotels, getHotel, listPlaces, getEvidence, addEvidence. Методы не получают React-компоненты и не возвращают JSX.

```ts
interface AgentProvider {
  reply(input: {
    trip: Trip;
    participantId: string;
    text: string;
  }): Promise<{
    text: string;
    updates: Array<{
      key: string;
      value: unknown;
      importance: 'required' | 'preferred';
      priority: number;
    }>;
    cityId?: string;
  }>;
}
```

Предлагаемый HTTP endpoint команды: `POST /v1/agent/reply`, JSON тела по AgentInput/AgentReply. Адаптер должен минимизировать передаваемый контекст: собственный диалог, общие нормализованные пожелания, данные поездки. Не передавать чужие личные диалоги из серверного Trip. В прототипе реальный HttpAgentProvider ещё не написан. После реализации добавить timeout, валидацию ответа и ограниченный retry. Поле updates лишь предложение, серверные use cases проверяют допустимые поля, автора и подтверждения.

В текущем mock-режиме свободное сообщение участника считается его явным редактированием собственных пожеланий. Обязательное условие не ослабляется автоматически из-за несовпадения. Организатор меняет общие параметры, личные пожелания редактирует только автор.

## Частичные данные

- Нет цены: «Цена уточняется», вариант требует уточнения.
- Нет характеристики: null + uncertain, не false и не положительный ответ.
- Конфликт: сохранить обе записи с разной областью, датой и ссылками conflictsWith.
- Устаревшее значение: validUntil + stale; не считать свежим.
- Нет подтверждённого фото номера: показывать отсутствие фотографии, не заменять её фасадом под видом номера.
- Нет маршрута: честное состояние недоступности, без нарисованной фиктивной прямой линии.

В текущем каталоге фото и маршруты подготовлены заранее. Реальные источники фото не распространяют реальность на цены, отзывы и георасчёты. Число confidence в будущем требует описания метода, оно не считается калиброванной вероятностью по умолчанию.

## Переключение

Сейчас поддерживаются fixture/json и оба варианта агента: mock/deepseek. `CATALOG_PROVIDER=api` и аналогичные значения дают конфигурационную ошибку 503. После реализации адаптера расширить серверный factory, а затем env. Нельзя сделать режим api простым alias для fixture. Сессии и голоса не зависят от типа поставщика каталога.
