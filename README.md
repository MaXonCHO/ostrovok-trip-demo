# Островок: моя поездка

Next.js-прототип: диалог с DeepSeek, подбор из базы, сохранённый профиль поездки и совместный выбор отеля. Новые страницы используют существующие шрифты PT Root UI/Spoof, светлый фон и компоненты Островка.

## Запуск

Нужен Node.js 22.14 или новее с `node:sqlite`.

```sh
npm ci
cp .env.example .env.local
# В .env.local укажите серверный DEEPSEEK_API_KEY
npm run dev
```

По умолчанию сайт: http://localhost:8080. Если порт занят:

```sh
npx next dev --hostname 0.0.0.0 --port 8081
```

Для production:

```sh
npm run build
PORT=8081 npm start
```

`GET /health` проверяет открытие БД, число импортированных отелей и наличие настройки DeepSeek, но не баланс провайдера. Без ключа доступны каталог, вход и совместный профиль; диалог сообщает о недоступном подключении, не заменяя ответы выдуманным агентом.

## Как пройти сценарий

### О!Блог

`/blog` — каталог 25 материалов о Петербурге из добавленной папки `ostrovok_blog_parser`, с поиском и рубриками под строкой поиска. Статьи сгруппированы в шесть подборок: название и описание, ведущая карточка в формате главной страницы (фото слева, текст справа), остальные материалы ниже каруселью. Стрелки исчезают на границах. В исходных данных нет статистики чтения, поэтому ведущие материалы обозначены «Выбор редакции»; при появлении достоверного поля `views` выбирается материал с наибольшим числом просмотров. Отдельный верхний блок с логотипом/кнопкой бронирования убран; заголовок — «Вдохновение для ваших путешествий от О!Блога».

`/blog/[slug]` — отдельная страница с кратким описанием, галереей, автором, датой и ссылкой на полный текст в О!Блоге. В исходном наборе нет полных текстов; они не генерируются и не подменяются краткими описаниями.

Во втором ряду главной, после осенних предложений, стоит блок с фотографией слева и описанием справа. Он выбирает одну статью по текущему пожеланию в строке ввода либо по сохранённым пользовательским сообщениям и подтверждённым предпочтениям поездки. Вопросы ассистента не считаются интересами пользователя. Подбор детерминированный и не требует дополнительного вызова DeepSeek; без интересов показывается гид по выходным.

Данные: `src/data/blog-articles.json`, 129 локальных фотографий: `public/ostrovok/blog/`. После обновления исходного набора запустите `npm run import:blog`. Папка парсера нужна только для повторного импорта, сайт работает с импортированными файлами.

Первый экран блога оформлен как главная: фотография, белый заголовок, стеклянная панель и белое поле поиска. Сетка и типографика совпадают с главной (`ostrovok-blog-alignment.css`). Под ведущей статьёй каждой подборки — полноширинный фотофон с компактными карточками без описаний. В последней фотосекции размещён финальный призыв начать поездку: тот же фон продолжается под текстом и кнопкой, отдельное изображение не добавляется. Кнопка возвращает на главную и фокусирует ввод пожеланий.

Рубрики проверены редакционно: актуалочка — 5, жильё — 4, места — 6, лайфхаки — 2, впечатления — 5, путеводители — 3. Новости LADA/Озёрной тропы находятся в актуалочке; глэмпинги — в жилье. Поиск и группировка используют единое правило `sectionForBlogArticle`.

Для текстов добавлен `ostrovok_blog_parser/article_text.py`: извлекает структурированные блоки из предоставленного локального HTML; сетевой `inspect` выводит только метрики. Сохранённые исходные карточки не переписывает. Пример из корня:

```sh
python3 ostrovok_blog_parser/article_text.py extract --html /path/to/article.html --url https://blog.ostrovok.ru/luchshie-kofejni-peterburga/ --output data/article-bodies/luchshie-kofejni-peterburga.json
npm run import:blog
```

Импортёр читает такие JSON из `data/article-bodies/` в `src/data/blog-bodies.json`. Страница статьи отображает заголовки, абзацы, списки, цитаты, таблицы и сопоставленные локальные фотографии без вставки сырого HTML.

По просьбе пользователя добавлены **25 пересказов** после сверки с оригиналами: конкретные места/идеи, по три раздела, абзацы и список. `content_kind=editorial_adaptation`, `recap=true`; на странице — метка «Пересказ статьи», дата материала-источника и ссылка на оригинал с авторством. Полные оригинальные тексты не копируются. Фотографии из существующей выгрузки расположены рядом с соответствующими объектами в тексте; обложка в теле не повторяется. Материалы-новости и сезонные программы явно относятся к датам исходных публикаций. Все 25 пересказов уже импортированы и доступны на `/blog/[slug]`.

### Планирование поездки

1. Откройте `/my-trip`, опишите поездку в Петербург. Уточняйте обязательные условия и пожелания. После каждого ответа меняются список, порядок и объяснения отелей.
2. Введите телефон подходящего формата и демо-код `0000`. SMS не отправляется. Гостевой черновик переносится в аккаунт.
3. Нажмите «Создать профиль поездки». Если условия не подтверждены, можно явно включить варианты из вкладки «Нужна проверка».
4. В профиле `/trips/[id]` изменяйте параметры, пересчитывайте подбор, создайте ссылку для спутников.
5. В другом браузере войдите с другим демо-телефоном, откройте приглашение и присоединитесь. Участники комментируют конкретные отели и голосуют. Организатор может закрепить отель, за который проголосовали все.
6. `/account` содержит сохранённые поездки. Повторный вход с тем же демо-телефоном восстанавливает аккаунт. `/favorites` хранит избранное в БД после входа.

Демо-вход не подтверждает владение телефоном: любой человек, знающий номер, может войти с `0000`. Это намеренное поведение прототипа, его нельзя использовать для настоящих персональных данных. Перед публичным запуском нужна замена на реальную авторизацию.

## Данные и пределы подтверждения

Источник: предоставленный `ostrovok_embedding_mvp.zip`. Файлы из `data/embedding/` содержат 300 карточек только Санкт-Петербурга. При первом обращении импортируются ID, названия, архивные описания, удобства, оценки, метрики OSM и происхождение данных. SHA-256 каталога хранится в `catalog_meta`, повторный запуск не создаёт дубликаты. Текущий сайт читает эти записи из SQLite, старый каталог 18 отелей оставлен только для совместимости с прежними контрактами и тестами.

В архиве отсутствуют актуальные цены, наличие, подтверждённые адреса, именованные POI, состав магазинов в ТЦ и пешие маршруты. Фотографии добавлены из обновлённого архива, с привязкой по стабильному hotel_id и сохранением источников. У всех записей `identity_verified=false`. OSM-метрики датированы 17.10.2026; расстояния рассчитаны по прямой от непроверенной геоточки. Число баров поблизости не доказывает тишину в номере. Интерфейс сохраняет эти ограничения и открывает исходную запись с источниками.

Обновление `ostrovok_mvp_FINAL_frontend.zip` подключено через `scripts/import-final-catalog.mjs` и `src/server/final-catalog.ts`. Runtime-данные — `data/final/`, изображения — `public/demo/final/`: 298 отелей с 682 WebP, у 81 объекта есть галерея. Два объекта без подтверждённой фотографии сохраняют нейтральный placeholder. Все пути и SHA-256 проверены, происхождение фото доступно в metadata/credits. `identity_verified` не повышается на основании найденной фотографии. Архивный фронтенд не используется. Промежуточная распаковка `data/incoming/` исключена из Git.

Движок задаётся явно через HOTEL_SEARCH_ENGINE=tfidf или e5. При E5 Next.js получает оценки всех 300 отелей от FastAPI по серверному E5_BASE_URL. FastAPI запускает настоящую [intfloat/multilingual-e5-small](https://huggingface.co/intfloat/multilingual-e5-small) на CPU, добавляет query: к запросу и сравнивает его с архивными нормализованными векторами 300×384. Проверяются хеш текстов, порядок hotel_id, нормы векторов и совместимость модели с тремя архивными строками.

Next.js сопоставляет оценки строго по hotel_id, проверяет полноту, дубли, модель, размерность и SHA-256 текстов. Затем применяет прежние строгие ограничения и метрики OSM, и только после этого ограничивает выдачу. SQLite, фото и интерфейс сохраняются. При E5 API возвращает engine=e5; при явном выборе TF-IDF возвращает engine=tfidf+facts. При недоступности E5 или несовпадении каталога возвращается 503, скрытого fallback нет. Диалог, профиль, голоса и рекомендованный порядок обычного поиска используют эту интеграцию.

Запуск FastAPI из корня проекта:

```bash
uv venv --python 3.12 .data/e5-venv
uv pip install --python .data/e5-venv/bin/python -r backend/e5/requirements.txt
OMP_NUM_THREADS=2 HF_HUB_DISABLE_XET=1 .data/e5-venv/bin/python -m uvicorn backend.e5.app:app --host 127.0.0.1 --port 8000
```

Первый запуск скачивает веса. Сервис привязывается к loopback. Для публикации отдельно настройте авторизацию и ограничения запросов. В .env.local сайта добавьте HOTEL_SEARCH_ENGINE=e5 и E5_BASE_URL=http://127.0.0.1:8000, затем перезапустите Next.js.

Проверка: /health сайта возвращает search=e5 и e5.ready=true; /api/planner/catalog/search?q=тихий%20отель возвращает engine=e5. Флаг all=1 возвращает весь список после ограничений вместо первых восьми вариантов. /api/health FastAPI показывает модель и реальные проверки совместимости. E5 оценивает смысловое сходство, но не подтверждает цены или инфраструктуру.


### Чтение, лайки и заметки

На странице статьи `ReadingEngagement` измеряет только видимое активное чтение. Одного открытия недостаточно: пассивный интерес появляется после 30 секунд и 65% прочитанного. Кнопка «Полезная статья» и сохранённая заметка — сильные сигналы. Для заметки пользователь выделяет фрагмент и нажимает «Сохранить заметку»; выделение без подтверждения ничего не записывает. Заметки проверяются по каноническому тексту статьи, доступны только владельцу, удаляются и содержат ссылку на исходную страницу.

На `/blog` есть отдельный блок «Заметки», который собирает сохранённые фрагменты со ссылками на статьи. `GET/POST /api/reading-interest`, `src/server/reading-interests.ts`, SQLite-таблицы `reading_interests` и `reading_notes`. Событие `ov:reading-updated` обновляет список. После входа гостевые записи переносятся в аккаунт.

`inferredReadingExpectations` добавляет мягкие предпочтения для нового подбора: гастрономия, культура, прогулки, семья, покупки. Явные отрицания и ограничения имеют приоритет; даты, бюджет и число гостей не подменяются. Например, заметка про пышки усиливает интерес к кафе/местной выпечке; база не содержит подтверждённой близости к конкретной пышечной. До подтверждения профиля предпочтения вычисляются заново, а не сохраняются как будто пользователь сказал их явно. При создании общего профиля текущие мягкие предпочтения фиксируются вместе с ним.

Все 25 статей расширены до примерно 370–405 слов: исходный пересказ отделён от собственных советов по планированию (`editorial_extensions`, `extension_start_index`). Изображения распределены по соответствующим абзацам, не идут подряд. В конце каждой статьи есть призыв начать поездку.


## Архитектура

```text
Страницы и существующая оболочка Островка
  AccountProvider / TripChat / LiveSelection / TripProfile
    POST /api/trip-chat
      JSON extraction DeepSeek → проверка профиля и пожеланий
      → детерминированное ранжирование → транзакция SQLite
    /api/planner/auth/*, trips/*, invite/*, favorites, catalog/*
      проверка сессии и членства → транзакции SQLite
```

- `src/server/database.ts`: схема v1, импорт, WAL, внешние ключи, индексирование.
- `src/server/planner-agent.ts`: адаптивный вопрос, структурированное извлечение, проверка диапазонов и явного смягчения обязательных условий. Провайдер не выбирает SQL, команды, голоса или ID отелей.
- `src/server/recommendations.ts`: обязательное известное противоречие исключает отель; неизвестное обязательное условие переводит его в отдельный список проверки. Мягкие пожелания влияют на порядок. Отсутствие удобства в неполной карточке не доказывает его отсутствие в отеле. Условия не ослабляются автоматически.
- `src/server/chat.ts`: сохранение собственной истории, идемпотентность по requestId, ограничение истории, общий таймаут провайдера 25 секунд, защита от записи устаревшего ответа.
- `src/server/workspaces.ts`: профиль, приглашения на 30 дней, членство, обсуждения, голоса и согласованный выбор. Новая ссылка отзывает предыдущую. Участнику не раскрываются телефон и личная переписка организатора.
- `src/server/auth.ts`: демо-телефон, ограничение попыток, одноразовый challenge, opaque-сессия в HttpOnly/SameSite cookie. В БД хранится хеш токена сессии. После входа гостевая сессия отзывается.
- Изменение пожеланий увеличивает ревизию, пересчитывает отели, снимает закрепление и требует новых голосов. Комментарии сохраняются. Новый участник также снимает прежнее закрепление. Одновременные изменения параметров проверяются по версии.
- Чужой trip ID не даёт доступа. Ссылка приглашения даёт краткий просмотр; доступ к обсуждению появляется после входа и присоединения. Текст комментариев выводится через React без HTML.
- Профиль обновляется опросом каждые 2,5 секунды в видимой вкладке. Нет необходимости во внешнем WebSocket-сервисе для локального прототипа.

## Хранение и Docker

По умолчанию БД: `.data/ostrovok.sqlite`, либо абсолютный `DATABASE_PATH`. Файлы БД, секреты и пользовательские записи исключены из Git. Права файла БД 0600. Для резервной копии используйте SQLite backup API или остановите сервер и скопируйте БД вместе с WAL; не копируйте один основной файл во время записи.

```sh
docker compose --env-file .env.local up --build -d
```

Compose монтирует постоянный том `planner-data` в `/app/data`. Не запускайте `docker compose down -v`, если нужно сохранить аккаунты и поездки. Контейнер работает от непривилегированного пользователя. `COOKIE_SECURE=true` включается за HTTPS. DeepSeek-ключ передаётся только серверу через окружение.

Vercel/serverless в текущем варианте не подходит для постоянной SQLite-БД: файловая система функции не обеспечивает сохранение записей между запусками. Используйте сервер с Docker и томом либо отдельно перенесите серверный слой хранения на управляемую БД. Установка `DATABASE_PATH=/tmp/...` не решает сохранность данных.

## Проверки

```sh
npm run typecheck
npm run lint
npm test
E2E_SERVER=1 E2E_BASE_URL=http://127.0.0.1:8081 npx playwright test tests/e2e/planner.spec.ts
```

Новый E2E проверяет рабочий вход через форму, перенос гостевого черновика, две сессии, доступ по приглашению, комментарии, единогласное закрепление, смену ревизии, CSRF, отсутствие горизонтального скролла на телефоне и WCAG-проверку основного содержимого. Использует только собственную тестовую поездку в локальной БД. Не запускайте этот тест против чужого сервера: путь `PLANNER_E2E_DATABASE` должен указывать на БД тестового сервера. Ранее существовавшие E2E сценарии карусели из трёх моковых отелей относятся к старой реализации; актуальный сценарий проверяет `planner.spec.ts`.

Реальные платежи, бронирование, доставка SMS и поставщик текущих цен не подключены. E5 требует запущенного FastAPI, описанного выше. Погода сохраняет прежнюю интеграцию Open-Meteo с явным различием прогноза, архива и сезонного ориентира.
