# Островок: моя поездка

Next.js-прототип: диалог с DeepSeek, подбор из базы, сохранённый профиль поездки и совместный выбор отеля. Новые страницы используют существующие шрифты PT Root UI/Spoof, светлый фон и компоненты Островка.

## Запуск

Нужен Node.js 22.14 или новее с `node:sqlite`.

```sh
npm ci
cp .env.example .env.local
# В .env.local укажите серверный DEEPSEEK_API_KEY
npm run dev
```

По умолчанию сайт: http://localhost:8080. Если порт занят:

```sh
npx next dev --hostname 0.0.0.0 --port 8081
```

Для production:

```sh
npm run build
PORT=8081 npm start
```

`GET /health` проверяет открытие БД, число импортированных отелей и наличие настройки DeepSeek, но не баланс провайдера. Без ключа доступны каталог, вход и совместный профиль; диалог сообщает о недоступном подключении, не заменяя ответы выдуманным агентом.

## Как пройти сценарий

1. Откройте `/my-trip`, опишите поездку в Петербург. Уточняйте обязательные условия и пожелания. После каждого ответа меняются список, порядок и объяснения отелей.
2. Введите телефон подходящего формата и демо-код `0000`. SMS не отправляется. Гостевой черновик переносится в аккаунт.
3. Нажмите «Создать профиль поездки». Если условия не подтверждены, можно явно включить варианты из вкладки «Нужна проверка».
4. В профиле `/trips/[id]` изменяйте параметры, пересчитывайте подбор, создайте ссылку для спутников.
5. В другом браузере войдите с другим демо-телефоном, откройте приглашение и присоединитесь. Участники комментируют конкретные отели и голосуют. Организатор может закрепить отель, за который проголосовали все.
6. `/account` содержит сохранённые поездки. Повторный вход с тем же демо-телефоном восстанавливает аккаунт. `/favorites` хранит избранное в БД после входа.

Демо-вход не подтверждает владение телефоном: любой человек, знающий номер, может войти с `0000`. Это намеренное поведение прототипа, его нельзя использовать для настоящих персональных данных. Перед публичным запуском нужна замена на реальную авторизацию.

## Данные и пределы подтверждения

Источник: предоставленный `ostrovok_embedding_mvp.zip`. Файлы из `data/embedding/` содержат 300 карточек только Санкт-Петербурга. При первом обращении импортируются ID, названия, архивные описания, удобства, оценки, метрики OSM и происхождение данных. SHA-256 каталога хранится в `catalog_meta`, повторный запуск не создаёт дубликаты. Текущий сайт читает эти записи из SQLite, старый каталог 18 отелей оставлен только для совместимости с прежними контрактами и тестами.

В архиве отсутствуют актуальные цены, наличие, подтверждённые адреса, фотографии, именованные POI, состав магазинов в ТЦ и пешие маршруты. У всех записей `identity_verified=false`. OSM-метрики датированы 17.10.2026; расстояния рассчитаны по прямой от непроверенной геоточки. Число баров поблизости не доказывает тишину в номере. Интерфейс сохраняет эти ограничения и открывает исходную запись с источниками.

Для Гельвеции сопоставлена ранее сохранённая галерея официального сайта (`src/data/fixtures/real-hotels.json`). Остальные записи показывают отсутствие фото, чужие изображения им не назначаются. Цены равны `null`, вымышленные тарифы и скидки не используются для рекомендаций. На страницах поиска неизвестная цена не проходит явно заданный жёсткий бюджет.

Архив содержит нормированные E5-векторы 300×384 и метаданные модели `intfloat/multilingual-e5-small`. Они сохранены в `data/embedding/`, но поиск в этом прототипе использует **текст и структурированные факты**, `engine=lexical+facts`. Query-encoder E5 не подключён. Нельзя сравнивать TF-IDF или иной произвольный вектор с E5-векторами. Для семантического поиска нужен отдельный сервис с той же моделью, префиксом `query:`, нормализацией и проверкой порядка ID. Windows `.venv` из архива не используется.

## Архитектура

```text
Страницы и существующая оболочка Островка
  AccountProvider / TripChat / LiveSelection / TripProfile
    POST /api/trip-chat
      JSON extraction DeepSeek → проверка профиля и пожеланий
      → детерминированное ранжирование → транзакция SQLite
    /api/planner/auth/*, trips/*, invite/*, favorites, catalog/*
      проверка сессии и членства → транзакции SQLite
```

- `src/server/database.ts`: схема v1, импорт, WAL, внешние ключи, индексирование.
- `src/server/planner-agent.ts`: адаптивный вопрос, структурированное извлечение, проверка диапазонов и явного смягчения обязательных условий. Провайдер не выбирает SQL, команды, голоса или ID отелей.
- `src/server/recommendations.ts`: обязательное известное противоречие исключает отель; неизвестное обязательное условие переводит его в отдельный список проверки. Мягкие пожелания влияют на порядок. Отсутствие удобства в неполной карточке не доказывает его отсутствие в отеле. Условия не ослабляются автоматически.
- `src/server/chat.ts`: сохранение собственной истории, идемпотентность по requestId, ограничение истории, общий таймаут провайдера 25 секунд, защита от записи устаревшего ответа.
- `src/server/workspaces.ts`: профиль, приглашения на 30 дней, членство, обсуждения, голоса и согласованный выбор. Новая ссылка отзывает предыдущую. Участнику не раскрываются телефон и личная переписка организатора.
- `src/server/auth.ts`: демо-телефон, ограничение попыток, одноразовый challenge, opaque-сессия в HttpOnly/SameSite cookie. В БД хранится хеш токена сессии. После входа гостевая сессия отзывается.
- Изменение пожеланий увеличивает ревизию, пересчитывает отели, снимает закрепление и требует новых голосов. Комментарии сохраняются. Новый участник также снимает прежнее закрепление. Одновременные изменения параметров проверяются по версии.
- Чужой trip ID не даёт доступа. Ссылка приглашения даёт краткий просмотр; доступ к обсуждению появляется после входа и присоединения. Текст комментариев выводится через React без HTML.
- Профиль обновляется опросом каждые 2,5 секунды в видимой вкладке. Нет необходимости во внешнем WebSocket-сервисе для локального прототипа.

## Хранение и Docker

По умолчанию БД: `.data/ostrovok.sqlite`, либо абсолютный `DATABASE_PATH`. Файлы БД, секреты и пользовательские записи исключены из Git. Права файла БД 0600. Для резервной копии используйте SQLite backup API или остановите сервер и скопируйте БД вместе с WAL; не копируйте один основной файл во время записи.

```sh
docker compose --env-file .env.local up --build -d
```

Compose монтирует постоянный том `planner-data` в `/app/data`. Не запускайте `docker compose down -v`, если нужно сохранить аккаунты и поездки. Контейнер работает от непривилегированного пользователя. `COOKIE_SECURE=true` включается за HTTPS. DeepSeek-ключ передаётся только серверу через окружение.

Vercel/serverless в текущем варианте не подходит для постоянной SQLite-БД: файловая система функции не обеспечивает сохранение записей между запусками. Используйте сервер с Docker и томом либо отдельно перенесите серверный слой хранения на управляемую БД. Установка `DATABASE_PATH=/tmp/...` не решает сохранность данных.

## Проверки

```sh
npm run typecheck
npm run lint
npm test
E2E_SERVER=1 E2E_BASE_URL=http://127.0.0.1:8081 npx playwright test tests/e2e/planner.spec.ts
```

Новый E2E проверяет рабочий вход через форму, перенос гостевого черновика, две сессии, доступ по приглашению, комментарии, единогласное закрепление, смену ревизии, CSRF, отсутствие горизонтального скролла на телефоне и WCAG-проверку основного содержимого. Использует только собственную тестовую поездку в локальной БД. Не запускайте этот тест против чужого сервера: путь `PLANNER_E2E_DATABASE` должен указывать на БД тестового сервера. Ранее существовавшие E2E сценарии карусели из трёх моковых отелей относятся к старой реализации; актуальный сценарий проверяет `planner.spec.ts`.

Реальные платежи, бронирование, доставка SMS, query-encoder E5 и поставщик текущих цен не подключены. Погода сохраняет прежнюю интеграцию Open-Meteo с явным различием прогноза, архива и сезонного ориентира.
