# Островок: передача контекста следующему чату Codex

Состояние на **27 октября 2026 года, Europe/Moscow**. Документ описывает фактически реализованный проект и согласованные с пользователем решения. Это снимок состояния, а не новое задание на разработку.

## 1. Суть проекта

Это прототип для хакатона Островка: пользователь описывает желаемую поездку обычным языком, помощник уточняет потребности и постепенно подбирает подходящие варианты отдыха и отелей.

Визуальная основа — сайт **Островок** и предоставленный пользователем брендбук. Уже собраны главная, выдача, страницы отелей, избранное и новый сценарий диалога «Моя поездка» с настоящим DeepSeek API.

**Текущее демо диалога работает только с Санкт-Петербургом.** Исходные данные остальных городов и фотографии сохранены. Старый прототип совместных поездок, голосований, сценариев и кабинета отельера был сознательно удалён при очистке проекта. Его упоминания в Git и старых документах не означают, что эта функциональность сейчас существует.

Основные материалы:

- [README.md](README.md) — запуск и краткое описание.
- [HACKATHON_CONTEXT.md](HACKATHON_CONTEXT.md) — исходная задача трека и требования хакатона.
- `Брендбук Островка/` — пользовательские материалы бренда.
- [docs/TZ_CODEX_OSTROVOK.md](docs/TZ_CODEX_OSTROVOK.md), [docs/voice-additions.md](docs/voice-additions.md) — более ранний контекст; часть старой архитектуры уже неактуальна.


```sh
npm run build
npm start
```

`scripts/start.mjs` читает `.env.local`/`.env`, копирует `public` и статику в standalone-сборку и запускает её на порту 8080. Подготовлены `Dockerfile` и `docker-compose.yml`; для передачи ключа в Compose:

```sh
docker compose --env-file .env.local up --build
```

Секрет DeepSeek пользователь уже добавил в корневой `.env.local`. Значение ключа в документацию не включалось. Образец конфигурации:

```env
DEEPSEEK_API_KEY=ваш_ключ
DEEPSEEK_MODEL=deepseek-flash
```

Переменная только серверная, без `NEXT_PUBLIC_`. `.env.local` исключён из Git и Docker-образа. Ключ проверялся: в клиентскую JS-сборку он не попадает. Повторно просить его у пользователя или выводить его значение для обычной работы не требуется.

В [AGENTS.md](AGENTS.md) есть требование читать подходящую документацию установленного Next.js из `node_modules/next/dist/docs/` перед изменением соответствующих механизмов: здесь используется свежая версия Next с отличиями от старых версий.

## 3. Пользовательский путь

1. На главной пользователь пишет пожелание или вводит его голосом. Примеры запросов доступны и на телефоне.
2. Кнопка «Фильтры» заменяет ввод на форму в той же области: направление, заезд/выезд, взрослые/дети/номера, переключатель «Только квартиры». «К пожеланиям» возвращает текст.
3. Заголовки и общая кнопка **«Подобрать отели»** не меняют положения при переключении режимов.
4. Нажатие «Подобрать отели» переводит на `/my-trip`, передавая пожелание и параметры. Заголовки главной уходят вверх, вопрос становится первым сообщением диалога. Переход использует View Transitions с запасным вариантом без этого API.
5. Помощник уточняет недостающие основы в порядке: **город → даты → бюджет за номер за ночь → участники**. Уже сообщённые сведения не запрашиваются заново. Можно явно отложить даты или отказаться от ограничения бюджета.
6. После подтверждения основ появляются **карточки типов отдыха** с фотографиями и короткими описаниями. Можно выбрать несколько и нажать «Продолжить».
7. Выбор отправляется в диалог как сообщение пользователя. Затем идут дополнительные вопросы: завтрак, тишина, расположение и прочие предпочтения.
8. Внизу постоянно доступны тематические подборки с каруселями отелей. Они видны уже во время первоначальной загрузки, а ответы уточняют темы и пул вариантов.
9. Карточка отеля открывает его страницу с галереей и демонстрационными тарифами. Избранное и выбор номера сохраняются локально.

На `/my-trip` активен пункт навигации «Моя поездка». Пункт **«Отели» возвращает на главную `/`**, а не в выдачу. Возвращение в «Мою поездку» восстанавливает сохранённую переписку.

## 4. Согласованный дизайн и поведение

Эти решения получены в ходе многочисленных пользовательских правок и важны при продолжении работы.

### Главная

- Первый экран занимает не больше **100svh**.
- Исходный фон — Алтай, `/ostrovok/home-cover.png`. На ПК он немного движется вслед за мышью; приближение для hero убрано. По краям есть запас изображения, чтобы не возникала пустая полоса.
- Заголовок: «Отели, в которых хочется остаться». Ниже: «Расскажите, куда хотите отправиться».
- Строка ввода прозрачная, на фотографии, с подчёркиванием и микрофоном. Она расположена ближе к синей кнопке, а не сразу под заголовком.
- Поле и форма фильтров резервируют одинаковое место: переключение не сдвигает заголовки и действие.
- Кнопка отправки общая для обоих режимов: одинаковые текст, форма, размер и положение.
- Подсказки на мобильном не скрываются: это горизонтально прокручиваемый ряд.
- Белая секция под первым экраном перекрывает фотографию округлой «шторкой». Прежний белый градиент на этом переходе убран.

Ниже сохранены блоки в стиле Островка: осенние предложения, мистические маршруты, гастрономические направления, сезонная подборка с паутиной, О!Блог и финальный призыв начать поездку. В сезонных блоках фотография закреплена относительно окна и открывается/перекрывается передними секциями при скролле.

Удалены по просьбе пользователя: старые преимущества, «Куда отправимся?», «Популярные направления», баннер «Поездка по вашим правилам», лишние маркетинговые подписи и сводка поиска на hero. Возвращать их как якобы пропавшую функциональность не нужно.

### Диалог

- **Нет большой белой оболочки чата.** Ответы ИИ — белым текстом прямо на фотографии; сообщения пользователя — компактные стеклянные плашки.
- Плашка пользователя: небольшой внутренний отступ, текст около 16px; не раздувать её до большой карточки.
- Новый ответ ИИ выводится постепенно по буквам. Сохранённые сообщения после обновления страницы не печатаются повторно. Полный текст доступен скринридеру; при `prefers-reduced-motion` показывается сразу.
- Блок подсказок, ввода и отправки закреплён на одной высоте в пределах первого экрана. История прокручивается над ним. Подсказки занимают зарезервированную строку и не двигают поле при изменении количества.
- Поле ответа компактное: одна строка по умолчанию, текст близко к линии; при вводе нескольких строк высота ограниченно растёт. Важен уже исправлявшийся дефект большого пустого промежутка между текстом и подчёркиванием.
- Скролл страницы к подборкам и футеру должен работать. В истории чата не используется `overscroll-behavior: contain`, который раньше создавал ловушку прокрутки.
- Старый блок «Ваша поездка» со сводкой, кнопками «Посмотреть все отели» и «Новый диалог» удалён по просьбе пользователя.

### Город и погода

- После подтверждения Петербурга фон меняется на пользовательскую фотографию Исаакиевского собора: `/ostrovok/petersburg-background.jpg`.
- Её исходник — `19.10.2-1-1280x560.jpg` в корне. Происхождение записано в `public/ostrovok/petersburg-background-source.json`.
- В корне также есть пользовательский файл `11.3-1280x560.jpg`; текущая CSS-ссылка фона ведёт именно на `petersburg-background.jpg`. Само наличие другого файла не означает его подключение.
- После подтверждения дат появляется **маленький значок погоды слева вверху**: иконка и диапазон температуры.
- Даты, пояснение и источник скрыты в подсказке: наведение, фокус с клавиатуры или нажатие на телефоне. Большой погодной панели в диалоге быть не должно.

### Подборки и типы отдыха

- Нижняя область — белая шторка с округлым верхом, как на главной.
- Каждая подборка: **название → небольшое описание → горизонтальная карусель отелей с фотографиями, городом и ценами**.
- Подборки не должны исчезать на этапе `basics`, во время запроса или при показе выбора типа отдыха. Карточки типов — дополнительный блок перед ними, а не замена подборок.
- Изначальные темы берутся из локального предварительного сопоставления пожелания; затем их уточняет модель. Если модель вернула пустой набор тем, интерфейс сохраняет/восстанавливает предварительные темы.
- Это правило не касается отелей: **пустой пул кандидатов остаётся пустым**, показывается объяснение, а не неподходящие варианты.
- Стрелки карусели — белые круглые кнопки поверх краёв фотографий. В начале нет левой, в конце нет правой; когда всё помещается, нет обеих. На телефоне доступен свайп.
- Типы отдыха: выходные, гастрономия, романтика, культура, с детьми, прогулки, бюджетно, спокойный отдых. Выбор множественный.

### Шрифты и футер

- Используются локальные **PT Root UI** для интерфейса и **Spoof Medium** для крупных заголовков. Шрифты из Островка, не системный заменитель и не старый Golos.
- Базовые заголовки главной: 36px на ПК / 24px на мобильных. Есть отдельные адаптивные роли; см. `ostrovok-type.css` и [аудит типографики](docs/typography-audit.md).
- Фотографии карточек плавно увеличиваются при наведении внутри рамки; сенсорные устройства и уменьшение движения учитываются.
- Новый футер воспроизводит текущий публичный Островок: логотип, магазины приложений, колонки ссылок, соцсети, платёжные знаки, нижняя юридическая часть. Активы локальные, происхождение — `public/ostrovok/footer/sources.json`.
- Футер расположен после подборок. Закреплённый фотофон ограничен границами сцены и не должен закрывать футер.

## 7. Диалог: контракты и состояние

Запрос `POST /api/trip-chat`:

```ts
{
  messages: { role: "user" | "assistant"; content: string }[];
  context: {
    search: { city: string; checkin: string; checkout: string;
              adults: number; children: number; rooms: number };
    wish: string;
    amenities: string[];
    maxPrice?: number;
    apartmentsOnly: boolean;
    source: "wish" | "filters";
  };
}
```

Ответ:

```ts
{
  message: string;
  suggestions: string[];
  hotelSlugs: string[];          // Финальные рекомендации.
  ready: boolean;
  collectionIds: string[];       // Темы редакционных подборок.
  candidateHotelSlugs: string[]; // Текущий допустимый пул, в том числе до ready.
  stage: "basics" | "trip-types" | "details" | "recommendations";
  profile: {
    city: "saint-petersburg" | null;
    checkin: string | null;
    checkout: string | null;
    tripType: string | null;
    datesFlexible: boolean;
    budgetMax: number | null;
    budgetFlexible: boolean;
    adults: number | null;
    children: number | null;
    rooms: number | null;
    tripTypeIds: string[];
  };
}
```

Все поля ответа обязательны. Для нового профиля есть `emptyTripChatProfile()`; его же используют при миграции сохранённого состояния. Даты — либо обе `null`, либо корректная ISO-пара с выездом позже заезда. Допускаются только известные ID тем и петербургских отелей.

**Критично различать `source`:** при `wish` значения `context.search` могут быть просто defaults и не являются пожеланиями пользователя. При `filters` переданные поля формы считаются выбранными. Сейчас defaults: Петербург, 6–9 ноября 2026, 2 взрослых, 0 детей, 1 номер.

Модель извлекает подтверждённый профиль из истории. `normalizeStage()` на сервере дополнительно обеспечивает порядок: первый неизвестный основной параметр → карточки типов → детали → рекомендации. Это не оставлено только на усмотрение промпта.

Типы отдыха отправляются как обычное сообщение `Выбираю тип отдыха: ...`. Модель сопоставляет названия с `tripTypeIds`. Текущие даты в серверном контексте вычисляются в `Europe/Moscow`, а не через произвольную часовую зону хоста.

История хранится в localStorage под ключом `ostrovok-trip-conversation-v1`. Это одна текущая переписка в браузере, не серверный аккаунт и не общая поездка нескольких людей. Новый запрос с главной имеет отдельный параметр `trip`; возвращение на `/my-trip` без нового запроса восстанавливает текущий диалог.

На сервер передаётся ограниченное окно истории: максимум 24 сообщения, каждое до 3000 символов, общий лимит 18000; клиент предварительно ограничивает окно примерно 16000 символами. Тело запроса ограничено 64 KiB. Ошибка/повтор не добавляют вторую копию пользовательского сообщения. Уход со страницы отменяет незавершённый запрос.

Избранное хранится отдельно: `ostrovok-demo-favorites-v1`. Серверной базы данных сейчас нет.

## 8. DeepSeek и уже исправленный реальный сбой

Сервер использует `https://api.deepseek.com/chat/completions`, модель по умолчанию `deepseek-flash`, `thinking: disabled`. Модель можно сменить серверной переменной `DEEPSEEK_MODEL`.

Проверенный реальный дефект: на ответе **«До 10 000 ₽ за ночь»** провайдер иногда возвращал HTTP 200 / `finish_reason=stop`, но `content` состоял только из пробелов. Обычный повтор JSON mode не помогал. Повтор в text mode возвращал нормальный вопрос, но без требуемой структуры, и тоже не проходил валидацию.

Текущий рабочий механизм:

1. Первая попытка — `response_format: json_object`, до 2000 токенов.
2. Допустимы BOM и внешняя Markdown-обёртка JSON; содержимое при этом строго проверяется.
3. При пустом, оборванном, синтаксически неверном или не соответствующем схеме ответе выполняется **один** повтор.
4. Повтор использует принудительный function-call **`submit_trip_reply`** с полной схемой всех полей, до 2400 токенов. Это транспорт структурированных данных; функция не исполняет внешних действий.
5. Принимается ровно один вызов известной функции; его arguments проходят ту же ручную валидацию. Неизвестные функции, ID, несколько вызовов или неверные аргументы отвергаются.
6. Обе попытки используют один общий таймаут 25 секунд и сигнал отмены клиента. Auth/rate/network ошибки не запускают бесконечные повторы.

Реальная проверка после исправления прошла: бюджет 10000 был принят, следующий вопрос — об участниках. При ошибке пользователь может нажать «Повторить», сохранив историю.

Не упрощать этот механизм до безусловного `JSON.parse(content)` и не заменять сбой локальным выдуманным ответом. Официальные материалы: [JSON Output](https://api-docs.deepseek.com/guides/json_mode/), [Tool Calls](https://api-docs.deepseek.com/guides/tool_calls/).

## 9. Погода

`GET /api/trip-weather?city=saint-petersburg&checkin=YYYY-MM-DD&checkout=YYYY-MM-DD`

Ответ содержит `label`, `description`, `temperatureMin`, `temperatureMax`, `sourceUrl`, `kind: forecast | seasonal | historical`.

- Поддерживается Петербург, период до 30 ночей, валидная пара дат.
- Ближайшие даты: Open-Meteo Forecast; прошлые: архив/исторические данные.
- Далёкое будущее: исторический аналог за завершённый год, явно подписанный как сезонный ориентир. Это не точный прогноз и не многолетняя климатическая норма.
- Общий сетевой бюджет 8 секунд, максимум один повтор, ограниченный кэш: прогноз около 10 минут, исторические/сезонные данные около суток.
- Исправлена особенность Forecast API: `past_days`/`forecast_days` не комбинируются со `start_date`/`end_date`; запрашивается окно, затем локально выбираются нужные дни.
- При ошибке цифры не выдумываются; в подсказке есть повтор получения погоды.

Источник: [Open-Meteo Forecast](https://open-meteo.com/en/docs), [Historical Weather](https://open-meteo.com/en/docs/historical-weather-api). API-ключ для этого сервиса не нужен.

## 10. Границы текущей реализации

- Диалог и структурированный подбор работают с настоящим DeepSeek, но каталог и параметры предложений локальные демонстрационные.
- В текущем UI один `candidateHotelSlugs` применяется ко всем выбранным темам. Отдельного ранжирования разных отелей внутри каждой темы пока нет.
- Голос — браузерное распознавание, анимация букв — клиентское раскрытие уже полученного ответа. Это не серверная потоковая генерация токенов.
- Бронирование, оплата, вход в реальный аккаунт, синхронизация между устройствами и серверное долговременное хранение не подключены.
- Нет реального сбора необычных свойств отелей, обхода источников, чтения отзывов, связи с отельерами, доказательной базы и реального расчёта гостиничных характеристик по геоданным. Это остаётся частью исходной задачи хакатона, а не готовой функцией.
- Темы из О!Блога — локально подготовленная редакционная база; запросов к блогу на каждый ход диалога нет.
- Глобальные редакционные блоки главной могут содержать другие города и страны. Ограничение Петербургом относится к текущему диалоговому демо, а не к каждому изображению главной.

## 12. Что помнить при продолжении

Главные согласованные ориентиры: стиль настоящего Островка, живые изменения на localhost, аккуратный диалог прямо на фото, понятные вопросы в правильном порядке, постоянные подборки внизу, сохранение истории и честное разделение демо-данных и подтверждённых фактов.

Последняя исправленная проблема — сбой формата DeepSeek после бюджета. Обход проверен реальным запросом. Нового задания сверх описанного состояния этим документом не назначается: дальнейшие изменения определяет пользователь.
